Săn memory leak trong JavaScript

App dùng ngày càng nhiều RAM mà không bao giờ nhả ra? Khả năng cao là bạn có memory leak. Chương này giải thích leak là gì và cách tìm nó bằng công cụ thay vì đoán mò.

1. Memory leak là gì?

Mỗi chương trình chiếm một vùng RAM. Khi vùng nhớ đó bị giữ lại ngoài ý muốn, ta gọi là rò rỉ (leak). Phần lớn leak do lỗi lập trình, và rất khó lần ra nếu không có công cụ.

Hermes (và mọi engine chạy trên máy ảo) có garbage collector (GC) — mã chạy định kỳ để quét các object và giải phóng những object không còn cần. (Vui: GC của Hermes tên là Hades.) GC rất thông minh, nhưng code của bạn vẫn có thể "đánh lừa" nó, khiến object còn được tham chiếu nên không bị thu dọn.

Tóm gọn

Leak xảy ra khi chương trình không giải phóng bộ nhớ mà nó không còn cần. Với JS: object vẫn còn đường tham chiếu từ "gốc" (root) tới nó, nên GC coi nó là còn dùng.

2. Ba kiểu leak hay gặp

① Listener không bao giờ ngừng nghe

const BadEventComponent = () => {
  useEffect(() => {
    const subscription = EventEmitter.addListener('myEvent', handleEvent);
    // ❌ thiếu cleanup → component unmount rồi mà listener (và handleEvent) vẫn sống
  }, []);
  return <Text>Listening for events...</Text>;
};

// ✅ sửa
useEffect(() => {
  const subscription = EventEmitter.addListener('myEvent', handleEvent);
  return () => subscription.remove();
}, []);

② Timer không bao giờ dừng

Lưu ý về sách

Bản PDF dán nhầm lại ví dụ listener ở mục này. Dưới đây là ví dụ timer đúng theo ý tưởng của sách.

useEffect(() => {
  const id = setInterval(() => tick(), 1000);
  // ❌ không clearInterval → callback (và mọi thứ nó capture) sống mãi
}, []);

// ✅ sửa
useEffect(() => {
  const id = setInterval(() => tick(), 1000);
  return () => clearInterval(id);
}, []);

③ Closure giữ tham chiếu tới dữ liệu lớn

class BadClosureExample {
  private largeData: string[] = new Array(1000000).fill('some data');
  createLeakyFunction(): () => number {
    // ❌ closure bắt cả `this` → giữ nguyên mảng largeData
    return () => this.largeData.length;
  }
}

class GoodClosureExample {
  private largeData: string[] = new Array(1000000).fill('some data');
  createEfficientFunction(): () => number {
    const length = this.largeData.length;  // ✅ chỉ bắt con số cần thiết
    return () => length;
  }
}

3. Săn leak bằng React Native DevTools

DevTools mới xây trên Chrome DevTools nên quen web là dùng được ngay. Tab Memory có ba cách profile:

Công cụDùng để
Heap snapshotChụp phân bổ bộ nhớ giữa các object JS tại một thời điểm.
Allocation instrumentation on timelineGhi các lần cấp phát theo thời gian; chọn một khoảng để xem object nào được cấp trong đó mà vẫn còn sống khi kết thúc → công cụ tốt nhất để cô lập leak.
Allocation samplingLấy mẫu cấp phát, chi phí thấp, hợp với tác vụ chạy lâu; cho số liệu gần đúng theo call stack.

Thí nghiệm của sách

let leakyClosures: Function[] = [];          // biến global giữ closure

const createClosure = () => {
  const newDataLeak = generateLargeData();     // mảng lớn
  return () => newDataLeak.forEach(d => d.id); // closure bắt newDataLeak
};

const createManyLeaks = () => {
  for (let i = 0; i < 10; i++) {
    const c = createClosure();
    leakyClosures.push(c);              // ❌ giữ tham chiếu để GC không thu được
    leakyClosures.forEach(fn => fn());
  }
};
  1. Mở DevTools → tab Memory → chọn Allocation instrumentation on timeline → Start.
  2. Gọi createManyLeaks vài lần trong ~30 giây rồi dừng.
  3. Đọc biểu đồ: thanh xanh dương = cấp phát còn sống; chuyển xám = đã được GC thu. Còn nhiều xanh → có leak.
  4. Chọn khoảng spike đầu tiên, xem danh sách constructor, mở rộng Function.
  5. So sánh hai cột: Shallow size (bộ nhớ riêng của object) và Retained size (bộ nhớ sẽ được giải phóng nếu object bị xóa).
Dấu hiệu nhận ra leak

JSFunction() có shallow size chỉ 40 byte nhưng retained size tới 2.772.088 byte! Một closure bé xíu đang níu cả mảng dữ liệu khổng lồ. DevTools còn chỉ đúng dòng code tạo ra nó.

Sửa & kiểm lại: bỏ việc push closure vào mảng global (chỉ gọi rồi thôi). Chạy profile lần nữa → toàn bộ thanh chuyển xám (trừ cái cuối chưa kịp thu) = hết leak.

GC không chạy tức thì

Vì GC chạy định kỳ, đối tượng chưa chắc biến mất ngay. Đôi khi cần cấp phát thêm thứ khác để kích hoạt thu dọn rồi mới kết luận.

Tóm tắt

Nguyên nhân

Listener, timer, closure, biến global vẫn tham chiếu object.

Cách sửa

Luôn cleanup trong useEffect; đừng bắt cả object lớn trong closure.

Công cụ

Allocation instrumentation; so shallow vs retained size.

Kiểm tra nhanh

1. Thanh xanh dương còn nguyên sau khi profile xong nghĩa là gì?
Xanh = còn cấp phát; xám = đã bị GC thu.
2. Retained size lớn hơn rất nhiều shallow size cho biết điều gì?
Retained size là phần bộ nhớ sẽ được trả lại nếu xóa object đó.
3. Cách đúng để tránh leak listener trong useEffect?
Hàm cleanup chạy khi unmount (hoặc trước effect kế tiếp).
