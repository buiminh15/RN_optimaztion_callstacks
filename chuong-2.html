JavaScript & React: cách profile và đo FPS

Mục tiêu của phần này: cải thiện FPS bằng cách tối ưu phía JS/React. Trước khi tối ưu, bạn phải học cách đo — đây là kỹ năng dùng ở mọi app.

1. React Native chạy JS ở đâu?

App React Native là một app native "có thêm" một chút: một phần code native chạy lên là của React Native. Ghép lại gồm Kotlin/Java (Android), Swift/Objective-C (iOS), C++ (lõi runtime) và JavaScript chạy bởi engine Hermes.

Khi khởi động (New Architecture), React Native lo ba việc:

Sơ đồ · Các luồng chính

Main (UI) thread
Khởi tạo lõi RN: React renderer (C++), JSI, engine Hermes, layout Yoga → vẽ UI native
⇅ giao tiếp qua JSI
JS thread
Chạy JavaScript: logic nghiệp vụ, React render, state
Native modules thread
Chạy các TurboModule được nạp lười (lazy)

Điểm mấu chốt: logic (JS thread) và vẽ (main thread) chạy ở hai luồng tách biệt.

Vì sao tập trung vào JS trước?

Khảo sát nội bộ 100 lập trình viên React Native của Callstack: 80% vấn đề hiệu năng đến từ phía JavaScript. Mẫu nhỏ nên chưa đại diện, nhưng đủ gợi ý: hãy xử lý JS trước khi sang tối ưu native ở Phần 2.

2. Mô hình re-render của React

Thư viện react rất nhỏ: chủ yếu là API, vài tính năng chung và thuật toán reconciliation — quyết định "cần làm gì" (what). Còn "làm thế nào" (how) giao cho renderer: react-dom (web), react-native (iOS/Android), react-native-windows…

React so sánh phần bạn thay đổi và chỉ áp dụng số cập nhật tối thiểu cần thiết. Một component re-render khi:

① Cha re-render
kéo theo mọi con (kể cả khi props không đổi)
② State đổi
gồm cả state từ hooks
③ Props đổi
④ Context đổi
⑤ Force update
lối thoát hiểm
Dễ nhầm

Nguyên nhân ① là thủ phạm hay gặp nhất: re-render không có nghĩa là props đổi. Ta sẽ thấy ngay trong ví dụ dưới.

Bổ sung: React docs – Render and Commit giải thích 3 bước trigger → render → commit mà Profiler hiển thị thành các "commit".

3. Profile React bằng React Native DevTools

Profiling là phân tích chương trình để tạo "hồ sơ" thực thi: phần nào tốn CPU/bộ nhớ nhất. Lý do: app quá phức tạp để đoán, và các tối ưu "mù" thường ít tác dụng. Quyết định phải dựa trên dữ liệu.

Ví dụ sẽ profile

export const App = () => {
  const [count, setCount]   = React.useState(0);
  const [second, setSecond] = React.useState(0);
  return (
    <View style={styles.container}>
      <Text>Welcome!</Text>
      <Text>{count}</Text>
      <Text>{second}</Text>
      <Button onPress={() => setCount(count + 1)}  title="Press one" />
      <Button onPress={() => setSecond(second + 1)} title="Press two" />
    </View>
  );
};

const Button = ({ onPress, title }) => (
  <Pressable style={styles.button} onPress={onPress}>
    <Text>{title}</Text>
  </Pressable>
);

Các bước

  1. Mở React Native DevTools. Nhấn j trong terminal Metro, hoặc mở Dev Menu (lắc máy · Cmd+M Android · Cmd+D iOS) → "Open DevTools".
  2. Chuyển sang tab Profiler (plugin React Profiler tích hợp sẵn).
  3. Bấm biểu tượng bánh răng, bật "Highlight updates when components render" và "Record why each component rendered while profiling".
  4. Bấm "Start profiling". (Khi profile lúc khởi động app, dùng "Reload and start profiling".)
  5. Tương tác: bấm "Press one" 2 lần rồi "Press two" 2 lần → 4 commit.
  6. Dừng và đọc kết quả ở Flame graph và Ranked.

Thử mô phỏng: ai re-render khi bấm nút?

Demo dưới mô phỏng đúng ví dụ của sách. Bấm nút rồi nhìn bộ đếm render ở từng component (cam = có render, xanh = bị bỏ qua).

Demo · Re-render simulator

Nhật ký commit

Khi chưa tối ưu, cả hai Button render ở mọi commit dù props không hề liên quan — vì cha App re-render (nguyên nhân ① ở trên). Trong Profiler bạn sẽ thấy hai component Button mỗi commit.

Cách đọc Profiler

Flame graph

Cây component theo thời gian render. Bấm vào thanh xanh (ví dụ View) để "zoom" vào con. Thanh vàng = tốn thời gian nhất.

Ranked

Xếp component từ chậm (vàng) đến nhanh (xanh) — giống "Bottom-up" ở các profiler khác.

Why did this render?

Cho biết lý do render (props đổi, state đổi, cha render…). Đây là thông tin quý nhất.

4. Sửa thủ công bằng memo + useCallback

// bọc hàm inline bằng useCallback
const onPressHandler = useCallback(() => setCount(count + 1),  [count]);
const secondHandler  = useCallback(() => setSecond(second + 1), [second]);

<Button onPress={onPressHandler} title="Press one" />
<Button onPress={secondHandler}  title="Press two" />

// bọc component bằng memo
const Button = memo(({ onPress, title }) => {
  // ...
});

Vì sao cần cả hai? memo so sánh props nông; nếu onPress là hàm inline mới mỗi lần render thì props luôn "khác" và memo vô tác dụng. useCallback giữ hàm ổn định giữa các lần render. Hãy tick ô "memo + useCallback" ở demo trên rồi bấm lại: chỉ nút vừa bấm re-render (vì count nằm trong deps của handler đó).

Nếu dùng React Compiler

Đoạn code gốc sẽ được tự động memoize (sách ghi nhận tên tự sinh như _c2 trong Profiler), nên ít re-render hơn mà không cần viết tay. Sẽ được bàn ở chương React Compiler.

Quy tắc thực hành

Tập trung vào component màu vàng (tốn thời gian) và dùng "Why did this render?". Với app thật, flame graph sẽ rối hơn nhiều so với ví dụ — hãy thử ngay trên app của bạn.

Bổ sung: React Native DevTools (docs chính thức) · React docs – memo.

5. Profile code JavaScript (CPU)

DevTools của React Native dựa trên Chrome DevTools nên cũng profile được CPU của JS thông thường. Dùng tab JavaScript Profiler.

Không thấy tab?

Bấm bánh răng góc phải → mục Experiments → bật JavaScript Profiler.

Chọn kiểu xem ở góc trái: Chart (flame chart), Heavy (Bottom-Up) (sắp theo hàm chạy lâu nhất) hoặc Tree. Thử với hàm chạy rất lâu:

const longRunningFunction = () => {
  let i = 0;
  while (i < 1000000000) { i++; }
};

Bắt đầu ghi, chạy hàm, dừng ghi. Kết quả: hàm chạy hơn 12 giây — suốt thời gian đó phần JS của app đứng im, nhưng UI native vẫn phản hồi nhờ mô hình luồng của React Native.

Demo · Flame chart (bấm vào từng thanh)

Mô phỏng profile ở trên. Mỗi hàng là một tầng của call stack; chiều rộng là thời gian.

Bấm vào một thanh để xem ý nghĩa.
Quy tắc 16 ms

Muốn đạt 60 FPS, không hàm nào nên chặn JS thread quá 16 ms; với 120 FPS là ~8 ms. Dùng thanh trượt để cảm nhận:

Demo · Một tác vụ chặn JS thread bao lâu thì rớt khung hình?

Thời gian tác vụ:
JS thread — mỗi vạch = một khung hình
0 → 200 ms
Khung hình trong 200 ms (đỏ = bị bỏ lỡ)

Đơn giản hóa: mỗi khung cần JS xử lý xong trong ngân sách để cập nhật UI kịp thời.

6. Đo FPS

Nếu app bị khựng, lag khi nhập liệu hoặc "giật" — UI đang rớt khung hình. Một khung hình là một lần vẽ lên màn hình; màn 60 Hz vẽ 60 khung/giây. Ngân sách: 16,6 ms ở 60 Hz, hướng tới 8,3 ms ở 120 Hz (xem demo ở Chương 1).

Perf Monitor có sẵn

Mở Dev Menu rồi chọn Show Perf Monitor. Một bảng nhỏ hiện ở góc trên-trái với hai chỉ số FPS: UI (Main) thread và JS thread — nhờ đó bạn biết ngay chậm do JavaScript hay do native.

Mở Dev Menu

iOS Simulator: Ctrl+Cmd+Z (hoặc Device → Shake) · Android emulator: Cmd/Ctrl+M · máy thật: lắc.

Đọc kết quả

JS FPS tụt, UI FPS ổn → vấn đề ở JS. UI FPS tụt → xem Phần 2 (Native).

Luôn tắt dev mode khi đo hiệu năng

Android: Dev Menu → Settings → JS Dev Mode. iOS: chạy Metro ở chế độ không phải dev (ví dụ release build). Dev mode làm số đo thấp hơn thực tế rất nhiều.

Khi FPS tụt lúc animation/tác vụ nào đó, dùng profiler ở mục 3–5 để thu hẹp nguyên nhân.

7. Flashlight — đo FPS trung bình (Android)

FPS trong Dev Menu dễ nhìn nhưng khó lưu và so sánh. Flashlight cho báo cáo kiểu Lighthouse (chỉ Android):

# mở app trên emulator Android, rồi:
> flashlight measure
  • Biểu đồ các chỉ số hiện theo thời gian thực khi bạn thao tác.
  • Báo cáo gồm điểm hiệu năng tổng, FPS trung bình, CPU, RAM.
  • Kết quả lưu ra file JSON → so sánh giữa các phiên bản code, dùng cho giám sát tự động để chứng minh FPS thật sự cải thiện.

Bổ sung: Flashlight trên GitHub (BAM) · React Native – Performance Overview.

Kiểm tra nhanh

1. Component Button render lại dù props không đổi. Nguyên nhân phổ biến nhất?
Cha re-render kéo theo mọi con trừ khi con được memo.
2. Bọc Button bằng memo nhưng vẫn truyền onPress={() => …} inline. Kết quả?
Hàm inline là tham chiếu mới mỗi lần nên so sánh props luôn thấy "khác". Cần useCallback.
3. Perf Monitor hiện FPS của hai luồng nào?
Nhờ vậy bạn phân biệt được chậm do JS hay do native.
4. Hàm chặn JS thread 50 ms ở 60 Hz làm rớt khoảng bao nhiêu khung?
50 / 16,7 ≈ 3 khung — bỏ lỡ khoảng 2–3 khung.
5. Công cụ nào lưu kết quả FPS ra JSON để so sánh giữa các phiên bản (Android)?
Flashlight xuất báo cáo JSON gồm FPS, CPU, RAM và điểm tổng.
