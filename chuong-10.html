Khác biệt giữa các nền tảng

Phần 1 cho thấy tới 80% vấn đề hiệu năng đến từ JS — nghĩa là vẫn còn ít nhất 20% nằm ở phía native. Phần 2 đi vào đó. Chương này dựng nền: vòng đời khởi động app, mô hình luồng, và bộ công cụ iOS/Android mà bạn sẽ dùng xuyên suốt.

1. Từ lúc chạm icon đến khi thấy UI

Hiển thị UI không đơn giản. Hãy xem trên Android:

  1. Khởi tạo process. OS tạo process và một sandbox bảo mật cho dữ liệu của app. Tùy cơ chế, OS có thể khởi tạo một phần hoặc toàn bộ trước cả khi bạn mở app — gọi là warm/hot startup (Android) hay prewarming (iOS).
  2. Khởi tạo application. OS gọi Application.onCreate, rồi tạo Activity và Activity.onCreate(). Đây là nơi code native khởi tạo và hành trình React Native bắt đầu.
  3. Vòng đời tiếp theo. Activity.onStart()… rồi UI thread xử lý layout, đo và vẽ view lên màn hình.
Khi đo thời gian khởi động

Luôn đo cold startup (process chưa tồn tại). Warm/hot/prewarming làm số đo đẹp hơn thực tế.

2. Mô hình luồng của React Native

Dân JS quen một luồng + event loop. Dân mobile quen hai loại: UI thread (vẽ giao diện) và background thread (việc nặng, business logic). Một thread là đơn vị thực thi nhỏ nhất của một process, chia sẻ bộ nhớ của process đó.

React Native mang mô hình khai báo của web vào mobile: phần lớn việc phân luồng được che giấu, renderer sẽ chạy code đúng luồng phù hợp. Event loop cũng có trong app RN — nằm trong renderer C++ Fabric và được Hermes truy cập.

Demo · Chuỗi khởi động React Native (Android)

Bấm từng bước để xem điều gì chạy ở đâu.

Cụ thể, sau khi native app khởi tạo, code Kotlin trong thư viện com.facebook.react:react-android khởi tạo Hermes, nạp JS bundle (thường ở dạng Hermes Bytecode – HBC, tránh bước thông dịch tốn kém) vào bộ nhớ và chạy trực tiếp trên JS thread (mqt_v_js). Trước khi chạy JS, nó xử lý các native module được đánh dấu chạy sớm (eager). Sau đó JS chạy, các TurboModule khởi tạo lười từ thread riêng (mqt_v_native) và việc render/sự kiện được lên lịch sang UI thread, nơi Fabric xử lý.

Chương sau sẽ dùng profiler của Android/iOS để tự quan sát các giai đoạn này.

3. Hai thế giới công cụ: Android Studio và Xcode

Dùng Expo?

Expo che bớt phần native (Dev Clients, Config Plugins…), nên bạn ít phải rời IDE quen thuộc. Nội dung phần này chủ yếu dành cho dự án dùng React Native Community CLI.

Nên dùng IDE của Google/Apple cho Android/iOS (bạn có thể viết Swift/Kotlin trong VSCode nhưng IDE gốc "bất khả chiến bại" hơn). Chúng có sẵn:

4. Quản lý dependency theo nền tảng

Một thư viện RN có thể gồm JS + iOS + Android. Autolinking tự phát hiện và liên kết các module dành riêng cho RN. Nếu dependency có code native nhưng không có cấu trúc module RN thì cần thêm bước thủ công.

So sánh · Dependency

npm registry (hoặc Yarn, PNPM, Bun). Gói có thể chỉ có JS hoặc kèm code native.

> npm install react-native-bottom-tabs

File cần để ý: package.json (dependency, script), node_modules, package-lock.json (khóa phiên bản).

CocoaPods. Thư viện RN đưa code native lên npm; CocoaPods trỏ tới đường dẫn cục bộ. Dependency iOS thuần (không phải thư viện RN) thì thêm vào Podfile:

# ios/Podfile
target 'HelloWorld' do
  pod 'SDWebImage', '~> 5.0'   # >=5.0 và <6.0
end

> cd ios && bundle exec pod install

~> 5.0 cho phép ≥5.0 <6.0; ~> 5.0.1 cho phép ≥5.0.1 <5.1. Dùng bundle exec để lấy đúng phiên bản CocoaPods theo Gemfile. Mở Xcode nhanh bằng xed .; luôn mở .xcworkspace chứ không phải .xcodeproj. File cần để ý: Podfile, Gemfile, Pods/ (không commit). RN chưa hỗ trợ Swift Package Manager.

Gradle. Module RN tham chiếu cục bộ từ node_modules/. Dependency Android thuần thêm thủ công vào android/app/build.gradle rồi sync:

dependencies {
  implementation 'com.github.bumptech.glide:glide:4.12.0'
}
> cd android && ./gradlew clean

Phiên bản: chính xác (4.12.0), khoảng (4.+), động (+ — không nên). Production: dùng phiên bản chính xác. File cần để ý: android/build.gradle, android/app/build.gradle, gradle.properties (cờ như Hermes), gradlew/gradlew.bat (Gradle Wrapper), .gradle/ (không commit). Xem task: ./gradlew tasks.

5. Build: ba thế giới khác nhau

So sánh · Quy trình build

JS được engine thông dịch lúc chạy; nhưng cần transpile để tương thích. Metro (bundler) dựa trên Babel để đưa cú pháp hiện đại về dạng Hermes hiểu được. Phiên bản JS hỗ trợ phụ thuộc phiên bản Hermes; preset Babel của RN luôn đồng bộ với engine.

Swift/Objective-C là ngôn ngữ biên dịch. Hệ thống build Xcode dùng Clang (Obj-C) và LLVM (Swift).

  1. Source Compilation → mã máy
  2. Linking code + framework + thư viện CocoaPods
  3. Signing bằng certificate & provisioning profile
  4. Packaging → .ipa

Gradle tự động hóa build/test/đóng gói. Java/Kotlin được biên dịch sang định dạng DEX cho Android Runtime (ART).

  1. Source Compilation → .class
  2. DEX Conversion → .dex
  3. Resource Processing (XML layout, ảnh, assets)
  4. Linking thư viện (Gradle)
  5. Signing bằng keystore
  6. Packaging → .apk / .aab

Kiểm tra nhanh

1. Khi đo thời gian khởi động nên dùng loại nào?
Warm/hot/prewarming có thể khởi tạo trước nên làm số đo đẹp hơn thực tế.
2. iOS dùng công cụ nào để quản lý dependency native trong RN?
RN chưa hỗ trợ SPM; CocoaPods là mặc định.
3. JS bundle ở dạng nào để Hermes chạy trực tiếp mà bớt thông dịch?
HBC được nạp vào bộ nhớ và chạy trên JS thread.
