Hiểu quản lý bộ nhớ native

Để săn memory leak native (chương 18), bạn cần biết ngôn ngữ native quản lý bộ nhớ ra sao: thủ công, đếm tham chiếu (ARC) hay garbage collector. Chương này là phần lý thuyết + thực hành cho C++, Kotlin và Swift.

1. Hai trường phái: thủ công và tự động

Thủ công (C, C++): bạn tự cấp phát và giải phóng. Dài dòng, dễ sai, nhưng đúng thì cho hiệu năng tốt nhất — phổ biến trong game. Tự động: dễ hiểu, dễ bảo trì — lựa chọn mặc định trong hầu hết trường hợp.

Tự động

Reference counting

Objective-C, Swift (ARC), cả Python, PHP. Mỗi tham chiếu tăng bộ đếm; hết phạm vi thì giảm; về 0 thì giải phóng ngay lập tức, chính xác.

⚠ Vòng tham chiếu (reference cycle): hai object giữ strong reference lẫn nhau → bộ đếm kẹt ở 1, không bao giờ giải phóng. Giải pháp: weak reference.

Tự động

Garbage Collector

JavaScript, Java, C#, Kotlin. GC chạy "độc lập", ví dụ Hermes tạo thread riêng chạy GC Hades; quét và giải phóng object không còn tiếp cận được.

Không lo vòng tham chiếu, nhưng thời điểm chạy không xác định; nếu GC không concurrent, app bị tạm dừng trong lúc GC → ảnh hưởng cảm nhận người dùng.

Thủ công

Stack & Heap

Stack: LIFO, tự cấp/giải phóng, rất nhanh nhưng nhỏ và gói trong phạm vi. Heap: lớn, cấp phát động (new/malloc), bạn phải tự giải phóng.

2. C++: smart pointer

Đã qua thời gọi new/delete thủ công mọi nơi: thư viện chuẩn có smart pointer giúp giảm leak. (Phần C++ giả định bạn biết con trỏ.)

KiểuĐặc điểm
std::unique_ptr<T>Sở hữu duy nhất; không copy, chỉ move.
std::shared_ptr<T>Đếm tham chiếu; nhiều chủ sở hữu. Phổ biến nhất, giống cơ chế của Obj-C/Swift.
std::weak_ptr<T>Đi kèm shared_ptr; truy cập object nhưng không tăng bộ đếm.

unique_ptr

void takeOwnership(std::unique_ptr<std::string> s1) {
  std::cout << *s1;   // tự xóa khi hàm kết thúc
}
int main() {
  auto str1 = std::make_unique<std::string>("Hello World");
  takeOwnership(std::move(str1));   // chuyển quyền sở hữu; str1 bị xóa tại đây
}

shared_ptr

void takeOwnership(std::shared_ptr<std::string> s1) { /* copy con trỏ → count+1; ra khỏi hàm → count-1 */ }
void takeReference(const std::shared_ptr<std::string> &s1) { /* tham chiếu → count không đổi */ }

auto str1 = std::make_shared<std::string>("Hello World");
takeOwnership(str1);   // vẫn dùng str1 được sau đó
takeReference(str1);   // không copy

Khi nào truyền gì? Truyền reference khi việc dùng shared_ptr trong hàm không sống lâu hơn caller; truyền by value khi cần nó sống độc lập với caller.

weak_ptr

void useWeakPtr(std::weak_ptr<std::string> weak) {
  if (auto shared = weak.lock()) {   // lock() → shared_ptr nếu object còn
    std::cout << *shared;               // an toàn; count tăng tạm thời
  } else {
    std::cout << "Object no longer exists!\n";
  }
}
auto str1 = std::make_shared<std::string>("Hello World");
std::weak_ptr<std::string> weak1 = str1;   // không tăng count (use_count() = 1)
useWeakPtr(weak1);   // còn
str1.reset();        // count → 0, object bị hủy
useWeakPtr(weak1);   // "Object no longer exists!"

3. Android (Kotlin/JVM)

Kotlin chạy trên JVM, dùng GC — giống JS, bạn vẫn có thể leak nếu quên giải phóng tài nguyên (không hủy đăng ký listener, không hủy tác vụ nền dài). Một công cụ chỉ dẫn GC là các container "weak" như WeakHashMap (JS có WeakMap): không giữ strong reference nên object bị thu ở lượt GC kế tiếp khi không ai khác tham chiếu.

val weakMap = WeakHashMap<String, String>()
run { weakMap[String("temp key")] = "some value" }   // size = 1
System.gc(); Thread.sleep(100)
println(weakMap.size)                               // 0 — đã bị thu

// WeakHashMap chỉ yếu với KEY. Muốn yếu với VALUE:
weakMap["key"] = WeakReference(LargeObject("1"))

4. iOS (Swift/Obj-C): ARC

do {
  let person1 = Person(name: "John")  // ref count: 1
  do {
    let person2 = person1             // ref count: 2 (KHÔNG copy!)
  }                                    // ra phạm vi → 1
}                                      // ra phạm vi → 0, giải phóng

5. Bốn nguồn memory leak

① Quên giải phóng (manual)

int main() {
  std::string *str1 = new std::string{"Hey"};
  std::cout << *str1;
  // ❌ quên delete str1 → leak
}
// ✅ delete str1;   hoặc tốt hơn: cấp phát trên stack
std::string str1 = std::string{"Hey"};

Hãy nghĩ hai lần trước khi đặt thứ gì lên heap (overhead lớn hơn stack đáng kể). Nhưng cũng đừng nhét quá nhiều lên stack — rủi ro stack overflow. Ưu tiên stack, dùng heap khi cần.

② Vòng tham chiếu

Nguyên nhân phổ biến nhất khi dùng reference counting. Thực tế vòng có thể trải qua nhiều class, rất khó tìm.

// C++                                    // Swift
class A { std::shared_ptr<B> b; };       class A { var b: B? }
class B { std::shared_ptr<A> a; };       class B { var a: A? }   // ❌ cycle

// Sửa: phá vòng bằng weak
class B { std::weak_ptr<A> a; };         class B { weak var a: A? }

Cách khác: tạo class thứ ba C giữ tài nguyên chung mà A và B cùng phụ thuộc — kỹ thuật refactor thường gặp ở JS.

③ Tài nguyên không được giải phóng (ngôn ngữ có GC)

Điển hình: pattern listener mà quên gỡ — bạn JS dev chắc đã quen. DataManager giữ strong reference tới listener nên MyClass không bao giờ bị GC:

class DataManager {
  private val listeners = mutableListOf<DataListener>()
  fun registerListener(l: DataListener)   { listeners.add(l) }
  fun unregisterListener(l: DataListener) { listeners.remove(l) }
}
class MyClass : AutoCloseable {                 // ✅ cleanup có chủ đích
  override fun close() { dataManager.unregisterListener(listener) }
}
// Hoặc lưu callback bằng WeakReference để tự xử lý:
private val listeners = mutableListOf<WeakReference<DataListener>>()

Kotlin không có destructor/deinit xác định, nên cần vòng đời cleanup như AutoCloseable.

④ Ghi đè thủ công (manual overrides)

Ngôn ngữ tự động thường có cách can thiệp thủ công, chủ yếu để tương tác với ngôn ngữ ngoài (C). Dùng sai là nguồn leak khó tìm. Swift có Unmanaged:

HàmTác dụng
passRetainedTạo Unmanaged, tăng ref count
passUnretainedTạo Unmanaged, không tăng
takeRetainedValueLấy object, giảm ref count
takeUnretainedValueLấy object, không ảnh hưởng
let obj = MyObject()                                 // 1
let unmanaged = Unmanaged.passRetained(obj)            // 2
let object1 = unmanaged.takeRetainedValue()            // 1  ✅ cân bằng

let u2 = Unmanaged.passUnretained(obj)                  // không đổi
let o2 = u2.takeRetainedValue()                         // 💥 CRASH: giảm xuống dưới 0
Quy tắc ngón tay cái

Luôn cân bằng retained/unretained: passRetained thì sau đó takeRetainedValue, và ngược lại. Có thể gọi toOpaque() để lấy con trỏ thô truyền cho C/C++.

Kiểm tra nhanh

1. Vì sao vòng tham chiếu gây leak trong ARC?
Giải pháp: weak reference (weak var, std::weak_ptr).
2. Điểm yếu của Garbage Collector?
Đó là đánh đổi so với ARC (giải phóng ngay, xác định).
3. std::unique_ptr khác shared_ptr ở chỗ?
shared_ptr mới đếm tham chiếu.
