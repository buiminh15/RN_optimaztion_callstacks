Atomic State Management

Một thay đổi ở state toàn cục có thể kéo re-render cả cây component, kể cả những nơi không hề dùng phần state đó. State "nguyên tử" giúp mỗi component chỉ đăng ký đúng phần mình cần.

1. Vấn đề: state ở quá cao trong cây

React dựng lại UI từ state/props/context mỗi lần; component re-render khi đầu vào đổi hoặc khi cha re-render. Re-render xảy ra càng cao trong cây thì càng dễ lan xuống các lá một cách không cần thiết. Điều này đặc biệt rõ với state toàn cục — thường thấy ở codebase dùng nhiều Context hoặc Redux: đổi một giá trị trong store có thể re-render cả những component không liên quan.

Ví dụ của sách: App giữ filter và todos, truyền xuống FilterMenuItem và TodoItem (chưa memo):

const App = () => {
  const [filter, setFilter] = useState('all');
  const [todos, setTodos]   = useState(initialState);
  const filteredTodos = todos.filter(t =>
    filter === 'active' ? !t.completed : filter === 'completed' ? t.completed : true);
  return (
    <View>
      {['all','active','completed'].map(f => <FilterMenuItem key={f} currentFilter={filter} onChange={setFilter} />)}
      {filteredTodos.map((todo, i) => <TodoItem key={i} item={todo} onChange={setTodos} />)}
    </View>
  );
};

Hệ quả: đổi filter hoặc todos đều khiến App, FilterMenu và mọi TodoItem re-render. Tick một todo cũng làm FilterMenu render lại dù nó không phụ thuộc todos. Profiler sẽ cho thấy lý do là "hook changed" hoặc "parent rendered".

3. State nguyên tử (atomic)

Hướng bottom-up: chia state thành các đơn vị nhỏ, độc lập gọi là atom. Thay vì một store tập trung lớn, mỗi atom có thể được cập nhật và subscribe riêng ngoài mô hình render của React → re-render nhắm đúng mục tiêu. Thư viện: Jotai, Zustand, Recoil… (Vui: Jotai = "state" trong tiếng Nhật, Zustand = "state" trong tiếng Đức.) Ví dụ dùng Jotai:

const filterAtom = atom("all");
const todosAtom  = atom(initialState);

// đọc + ghi atom
const FilterMenuItem = ({ title, filterType }) => {
  const [filter, setFilter] = useAtom(filterAtom);
  return <TouchableOpacity onPress={() => setFilter(filterType)}><Text>{title}</Text></TouchableOpacity>;
};

// chỉ ghi: KHÔNG subscribe → không re-render khi todos đổi
export const TodoItem = ({ item }) => {
  const setTodos = useSetAtom(todosAtom);
  return (
    <TouchableOpacity onPress={() => setTodos(prev =>
      prev.map(t => t.id === item.id ? { ...t, completed: !t.completed } : t))}>
      {/* ... */}
    </TouchableOpacity>
  );
};

Demo · Đếm số lần render: state tập trung vs atom

Chọn cách quản lý state rồi bấm các thao tác. Số trong ô là số lần component đó đã render.

Kết quả với atom: đổi filter → re-render mọi thứ đọc filterAtom (các FilterMenuItem) và nơi dùng kết quả lọc (root + TodoItem). Tick todo → chỉ component subscribe todosAtom render lại; FilterMenuItem đứng yên, không cần memo.

Có nên đổi thư viện chỉ vì hiệu năng?

Atomic state giúp giảm re-render suốt nhiều năm (qua hooks và useSyncExternalStore). Nhưng nay đã có React Compiler, việc di chuyển cả app sang thư viện mới chỉ để tối ưu render có thể là không khôn ngoan khi compiler làm phần nặng giúp bạn. Chọn atomic khi nó cũng hợp mô hình dữ liệu của bạn.

Bổ sung: Jotai · Zustand · React – useSyncExternalStore.

Kiểm tra nhanh

1. Atom là gì?
Atom là đơn vị state tối thiểu; component chỉ re-render khi atom nó đọc thay đổi.
2. Vì sao useSetAtom tốt cho TodoItem trong ví dụ?
Không đọc giá trị → không phụ thuộc → không bị kéo render.
3. Có React Compiler rồi thì atomic state…?
Compiler giải quyết nhiều re-render thừa mà không cần đổi thư viện state.
