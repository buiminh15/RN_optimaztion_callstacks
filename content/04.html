Uncontrolled Components

React "vẽ lại cả cây" mỗi khi state đổi — một abstraction tiện lợi nhưng không miễn phí. Khi cần, ta có thể "thoát" khỏi nó bằng ref. Ví dụ điển hình: TextInput.

1. Lối thoát hiểm của React

Mọi abstraction đều đơn giản hóa thực tế và đánh đổi bằng độ chính xác, nên tốt nhất là có "lối thoát". React có refs, cho phép bỏ qua logic re-render. Component không bị điều khiển bởi state gọi là uncontrolled component.

2. TextInput controlled trong kiến trúc cũ

const DummyTextInput = () => {
  const [value, setValue] = useState("Text");
  const onChangeText = (text) => setValue(text);
  return <TextInput onChangeText={onChangeText} value={value} />;
};

Mỗi ký tự gõ vào: native → onChangeText (thao tác 1) → React setState → đồng bộ lại giá trị xuống native (thao tác 2). Lợi ích: React là nguồn sự thật duy nhất, bạn có thể validate, che (mask) hay biến đổi input ngay khi gõ.

Nhược điểm lộ ra khi tài nguyên hạn chế (máy Android yếu, JS đang tính toán nặng) và người dùng gõ nhanh: các cập nhật đến không đúng thứ tự. Trong kiến trúc async cũ, state React có thể lệch với native.

New Architecture

Vấn đề mất đồng bộ của controlled TextInput không nên còn trong New Architecture. Kiến thức này vẫn hữu ích cho app cũ và để hiểu cơ chế.

4. Giải pháp: bỏ prop value

<TextInput
  onChangeText={onChangeText}
-  value={value}
/>

Dữ liệu giờ chỉ đi một chiều: từ native (RCTSinglelineTextInputView trên iOS, AndroidTextInputNativeComponent trên Android) lên JS. Native tự giữ state nội bộ của ô nhập nên không còn đồng bộ ngược → hết nhấp nháy.

Kiểm tra nhanh

1. Uncontrolled TextInput khác controlled ở điểm nào?
Bỏ value → dữ liệu chỉ chảy native → JS.
2. Nguyên nhân gốc của lỗi "TES → TE → TET"?
Cập nhật cũ ghi đè giá trị mới hơn trong lúc người dùng vẫn đang gõ.
3. Lợi ích chính của controlled input?
React là nguồn sự thật duy nhất nên có toàn quyền với giá trị.
