Phân tích kích thước app bundle

Kích thước app quyết định việc người dùng có cài hay không, nhất là khi dùng dữ liệu di động. Chương này giới thiệu các định dạng đóng gói và công cụ đo kích thước cho Android và iOS.

1. Vì sao quan tâm kích thước app?

Google từng thử nghiệm mối liên hệ giữa kích thước APK và số lượt tải: cứ tăng 6 MB, tỷ lệ chuyển đổi cài đặt giảm 1%.

Demo · Mỗi 6 MB làm mất ~1% lượt cài

Tăng kích thước:

≈ mất tỷ lệ chuyển đổi cài đặt (ước lượng tuyến tính từ con số của Google).

Hai loại kích thước:

Network-bound

Download size, update size — dữ liệu nén truyền qua mạng.

Storage-bound

Install size, storage size — dung lượng giải nén của app và cache trên thiết bị.

2. Nền: các định dạng đóng gói

Hai định dạng: APK và AAB, chứa code native cho nhiều kiến trúc:

ABIDành cho
armeabi-v7aARM cũ, cấp thấp
arm64-v8aARM 64-bit, hiệu năng tốt hơn
x86Thiết bị Intel
x86_64Intel 64-bit

Cấu hình qua reactNativeArchitectures trong android/gradle.properties. Build nhiều kiến trúc làm build lâu hơn; khi phát triển với RN CLI, thêm --activeArchOnly vào run-android để nhanh hơn.

  • APK: định dạng truyền thống (phát triển, test, phân phối ngoài Play Store). Thực chất là file ZIP. Không tối ưu theo kiến trúc nên thường gói nhiều kiến trúc → to.
  • AAB: định dạng mới của Google, chứa những gì cần để sinh APK theo yêu cầu. Bắt buộc cho Google Play; Play tạo APK tối ưu cho từng thiết bị → giảm kích thước tải.

Thư viện: .a (C/C++, tĩnh), .aar (Android Archive: class + tài nguyên, tĩnh), .so (shared, động).

Hai định dạng: IPA và APP; kiến trúc: arm64 (thiết bị hiện đại) và x86_64 (simulator trên macOS).

  • IPA: để phân phối qua App Store, ad hoc, enterprise. Là archive chứa mọi thứ để cài app. (Vui: đổi .ipa thành .zip để xem bên trong; .apk cũng vậy!) App Store dùng nó để app thinning: App Slicing (chỉ gửi tài nguyên cần cho thiết bị), On-Demand Resources, Bitcode.
  • APP: thư mục chứa tài nguyên, binary, metadata — dùng khi phát triển trên simulator, không để phân phối.

Thư viện: .a (tĩnh), .dylib (động), .framework (động, một nền tảng), .xcframework (động, nhiều nền tảng/kiến trúc).

Tĩnh hay động?

Apple khuyên tránh thư viện động khi có thể để khởi động nhanh hơn (iOS nạp mọi dynamic library trên đường khởi động). Nhưng nếu chia sẻ một framework cho nhiều target (app, share extension, widget), link tĩnh sẽ nhân bản framework cho mỗi target (3 target = 3 bản). Khi đó chuyển sang link động loại bỏ trùng lặp — Emerge Tools có bài minh họa trực quan.

Tĩnh vs động

Tĩnh: gộp vào code app lúc biên dịch → một file thực thi; đơn giản, nhất quán, nhưng APK lớn hơn, build lại tốn hơn, có thể tốn RAM hơn do nạp cùng code nhiều lần. Động: nạp lúc chạy, chia sẻ giữa chương trình, cập nhật không cần biên dịch lại.

3. Đo kích thước Android: Ruler (Spotify)

Plugin Gradle dễ dùng: phân tích bundle debug/release cho từng kiến trúc.

  1. Thêm vào build.gradle cấp project: 
    buildscript {
  dependencies {
    classpath("com.spotify.ruler:ruler-gradle-plugin:2.0.0-beta-3")
  }
}
  2. Áp dụng plugin trong app/build.gradle: apply plugin: "com.spotify.ruler"
  3. Cấu hình kiến trúc, locale, mật độ màn hình, SDK: 
    ruler {
  abi.set("arm64-v8a")      // ABI = Application Binary Interface
  locale.set("en")
  screenDensity.set(480)
  sdkVersion.set(34)
}
  4. Chạy task mới analyzeDebugBundle / analyzeReleaseBundle: 
    > cd android
> ./gradlew analyzeReleaseBundle
# → Wrote HTML report to .../android/app/build/reports/ruler/release/report.html

Báo cáo cho download size và install size, kèm bảng phân rã các thành phần nội bộ/bên ngoài từ lớn đến nhỏ.

Ví dụ của sách

App mẫu tối ưu bằng R8: download 6,3 MB. Cùng app không có tối ưu build-time: 9,5 MB. (Xem Chương 25.)

Kiểm tra kích thước trong CI

Lý tưởng là tự động theo dõi kích thước và, ví dụ, bình luận lên PR GitHub. Ruler cho đặt ngưỡng và làm fail build khi app quá to:

ruler {
  verification {
    downloadSizeThreshold = 20 * 1024 * 1024   // 20 MB
    installSizeThreshold  = 50 * 1024 * 1024   // 50 MB
  }
}

4. Đo kích thước iOS

  • App Store Connect (hoặc TestFlight): chính xác nhất — kích thước từng biến thể và cảnh báo vượt giới hạn tải qua dữ liệu di động. Bản TestFlight to hơn App Store (có dữ liệu test). Sau xử lý của App Store (thêm DRM, nén lại) kích thước cuối có thể tăng nhẹ so với binary tải lên — bình thường.
  • Xcode (lúc phát triển): báo cáo ước lượng gần đúng.
  1. Tạo IPA đã ký trong Xcode.
  2. Ở Organizer: Distribute App → Custom → chọn kiểu phân phối → ở App Thinning chọn "All compatible device variants". (Tương đương trong ExportOptions.plist: <key>thinning</key><string>&lt;thin-for-all-variants&gt;</string> nếu chạy bằng xcodebuild.)
  3. Thư mục xuất gồm: IPA universal (mọi biến thể, cho thiết bị cũ), IPA thinned cho từng biến thể, và file App Thinning Size Report.txt.
App Thinning Size Report for All Variants of SampleApp
Variant: SampleApp-FB829A90-....ipa
App size: 3,5 MB compressed, 10,6 MB uncompressed

Compressed = download size; uncompressed = install size trên thiết bị.

5. Emerge Tools (trả phí, dùng thử 14 ngày)

Tác giả không có liên hệ tài chính với Emerge Tools nhưng dùng thường xuyên. Upload IPA/APK/AAB, dùng X-Ray hoặc Breakdown để xem thông tin nhị phân dưới dạng các ô chữ nhật bấm được (như source-map-explorer, nhưng cho binary Android/iOS).

Cẩn thận với "insight"

Công cụ cũng đưa gợi ý nhưng chưa đáng tin hoàn toàn — chẳng hạn nó từng đề xuất loại bỏ cả engine Hermes, điều sẽ làm app hỏng. Không phải insight nào cũng đáng làm theo.
