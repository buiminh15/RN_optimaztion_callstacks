Săn memory leak native

Khó phát hiện leak nếu không có công cụ chuyên dụng. May mắn là cả iOS và Android đều có công cụ tốt, tương tự profiler bộ nhớ JS ở Chương 3.

Hai nền tảng · Hai quy trình

Bước 1 — Memory Report (nhanh)

Build app trong Xcode, khi chạy mở Debug Navigator (panel bên) → Memory Report: đồ thị bộ nhớ app dùng. Nên dùng trên bản release. Đồ thị giúp phát hiện nhanh bộ nhớ tăng mãi, nhưng muốn biết nguồn leak cần Instruments.

Bước 2 — Instruments → Leaks

  1. Menu Product → Profile.
  2. Sau khi build xong, chọn template Leaks → Choose.
  3. Bấm nút ghi (góc trên trái), trên thiết bị thực hiện các bước nghi gây leak (điều hướng sang màn hình có native code, bấm nút…).
  4. Leaks hiện dấu đỏ khi phát hiện leak. Bấm vào để xem tóm tắt object bị leak, thư viện và frame chịu trách nhiệm; bên phải là stack trace chỉ đúng hàm.
  5. Bấm đúp tên hàm → Xcode mở mã nguồn.
Ví dụ của sách

Hàm C++ createNewStrings() cấp phát chuỗi trên heap nhưng quên delete (đúng lỗi ở Chương 13). Thêm delete rồi chạy lại → Leaks không còn báo gì.

Bước 1 — Track memory consumption

Build bản release, mở tab Profiler ở góc dưới trái → chọn Track memory consumption để xem đồ thị bộ nhớ.

Bước 2 — Một leak "thực tế" hơn: Activity bị giữ

Mặc định Android tạo lại MainActivity khi cấu hình đổi (xoay màn hình, đổi dark mode…). React Native tắt hành vi này bằng android:configChanges trong manifest, nhưng app native thì thường gặp. Cộng thêm một singleton toàn cục dùng listener pattern → công thức hoàn hảo cho leak.

object EventManager {
  private val listeners = mutableListOf<Callback>()
  fun addListener(callback: Callback)    { listeners.add(callback) }
  fun removeListener(callback: Callback) { listeners.remove(callback) }
}
interface Callback { fun onEvent() }

class MainActivity : AppCompatActivity(), Callback {
  override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    EventManager.addListener(this)     // ❌ không bao giờ removeListener
  }
  override fun onEvent() { Log.d("MAIN_ACTIVITY", "Hey") }
}

Ở vùng đánh dấu 2: MainActivity được cấp phát 4 lần nhưng giải phóng 0 lần → các Activity cũ vẫn bị EventManager tham chiếu, GC không thu được. Nhanh chóng có thể dẫn tới crash.

Lời kết

Thực tế app không hay leak, nhưng khi có thì việc tìm nguồn bị hầu hết lập trình viên "sợ". Có đúng công cụ, bạn sẽ xác định được nguyên nhân và tối ưu để app dùng ít bộ nhớ hơn — tránh bị OS giết sớm.

Bổ sung: Apple – Memory use · Android – Memory Profiler · LeakCanary (công cụ cộng đồng tự động phát hiện leak Activity).

Kiểm tra nhanh

1. Template nào của Instruments dùng để tìm leak?
Leaks đánh dấu đỏ và chỉ ra hàm gây leak.
2. Vì sao MainActivity bị leak trong ví dụ?
Cần removeListener khi Activity bị hủy.
3. Nên đo bộ nhớ trên bản build nào?
Debug thêm nhiều overhead làm số liệu sai lệch.
